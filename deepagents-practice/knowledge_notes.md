## ① Python 语言基础 → [`notes/py-basics.md`](notes/py-basics.md)

跨项目通用，换个库照样用。

| 知识点 | 一句话 |
|---|---|
| 函数签名与类型注解 | 注解是"说明"不是校验，运行时不拦你 |
| 装饰器 | `@xxx` 把函数**替换成另一个对象** |
| docstring | 函数体第一行的三引号字符串，运行时可读（`.__doc__`） |
| 类与继承 | 子类白拿父类一切，可覆盖其中几个方法 |
| 类 vs 实例 | `type(类)` 得到**元类**；`type(类())` 才是你要的 |
| `self` | 实例方法第一个参数，Python 自动传入，漏了就错位 |
| 覆盖父类方法 | 签名只能**放宽**不能**收紧**（里氏替换） |
| `**kwargs` | 把多出来的关键字参数打包收下，不报"不认识" |
| `isinstance()` vs `type()==` | 前者认继承，后者只认完全相同 |
| `type()` 是函数不是方法 | 写 `type(x)`，不是 `x.type()` |
| 自省三件套 | `type()` 是什么、`vars()` 存了什么、`dir()` 能访问什么 |
| `property` | 属性不等于数据 —— 可能是每次访问现算的 |
| 单元素元组 | `("hi")` 是字符串，`("hi",)` 才是元组 —— **差别只在一个逗号** |
| 注解的另一面 | `@tool` 会**用**注解校验并转换参数（`"1"` → `1`） |
| 没有 `virtual` | Python 所有方法默认可覆盖；契约由**调用方**在运行时强制 |
| Pydantic 私有属性 | 下划线类属性会被接管，`if not _flag` 恒为假 |

## ② Agent / LangChain 概念 → [`notes/agent-core.md`](notes/agent-core.md)

这个框架特有的 API 与协议。

| 知识点 | 一句话 |
|---|---|
| 工具对象不是函数 | `@tool` 后要用 `.invoke()`，不能用 `()` |
| `__doc__` vs `.description` | 装饰后 `__doc__` 拿到的是**类**的文档，你的描述在 `.description` |
| `invoke()` 的第二个参数 | 是 `config`，不是第二个工具参数 |
| `args` 键名 | 必须和函数参数名**一字不差**，否则 `Field required` |
| `bind_tools` | 框架靠它把工具清单交给模型；父类是**空壳**，必须自己覆盖 |
| 假模型的 `responses` | 按顺序发放的固定回答，**必须是消息对象**不能是字典 |
| 字段类型就是契约 | `list[BaseMessage]` 拒绝字典，创建时就报错 |
| `AIMessage.tool_calls` | 模型"举手"要调工具的方式，`content` 留空 |
| 工具出错不崩流程 | 错误会变成 `ToolMessage`（`status='error'`），**去看 status** |
| 消息的 `.type` | `'human'` / `'ai'` / `'tool'`，按种类分支最方便 |
| 消息的简写 | `("user", "内容")` 等价于 `HumanMessage(...)` |
| 输入是状态字典 | 键名写错**不报错、直接丢弃** |
| Harness 的工具来自哪 | 认工具就是认中间件：`Filesystem` 出 7 个、`SubAgent` 出 `task` |
| `tool.args` | 工具的「说明书」：参数名和约束都在里面 |
| Agent 状态的两个键 | 没挂 Todo 中间件时只有 `messages` 和 `files` |
| 虚拟文件的结构 | 是字典不是字符串，正文在 `content` 里 |
| 默认后端不落磁盘 | `StateBackend` 把文件存进状态，磁盘上找不到 |
| `write_todos` 整份替换 | 每次调用用新列表覆盖，状态只留最新一版 |
| `todos` 是独立状态字段 | 和 `messages` 分开存；没调用过就没有这个键 |
| v0.7 可选能力靠中间件 | `write_todos` 要显式加 `TodoListMiddleware`，看注册表差集最直接 |
| 子 Agent 是字典 | `name` / `description` / `system_prompt` 必填，靠 `task` 调起 |
| `tools` 完全替换 | 子 Agent 显式写 `tools` 后不继承主 Agent 的自定义工具 |
| 上下文隔离 ≠ 文件隔离 | 中间调用不进主消息，但共用 Backend 的文件仍在主状态里 |
| 子 Agent 过程要外部取证 | 隔离后主消息里查不到，只能在工具内记一笔 |
| `skills` 给的是父目录 | `["/skills/"]` 扫子目录；写成 `SKILL.md` 路径不报错，只是技能不加载 |
| 匹配只看 description | 启动时只有 name + description + 路径，正文不在上下文里 |
| `ls` 不算读到 | 正文要等 `read_file` 的 `ToolMessage` 回上下文才出现 |
| Skill 是文本即行为 | 改 `SKILL.md` 就改行为，代码不用动；但产物得单独断言 |

## ③ 调试与验证方法 → [`notes/method.md`](notes/method.md)

"我怎么知道自己做对了" —— 最容易忽略，但最值钱。

| 知识点 | 一句话 |
|---|---|
| 能创建 ≠ 能用 | 只测"造出来了"不够，要调用它、还要检查结果 |
| 怎么证明对象被替换 | 对比 `type(x)` 和 `type(x.func)` —— 给事实，不给一次失败的经历 |
| 怎么读 `ValidationError` | 字段名 + 缺什么 + 为什么；发生在创建**之前** |
| 看报错看"哪一层炸的" | 从下往上找第一个属于**你的代码**的栈帧，那才是问题起点 |
| 用干净环境隔离变量 | 错误可能来自"环境残留"时，换个干净环境跑，次要症状消失、根因才露出来 |
| 虚拟文件去状态取证 | 磁盘上找不到是正常的，别误判成自己写错了 |
| 断言前先归一化 | 路径有多种写法时，先统一形式再比较 |
| 看状态流转变用 `stream(values)` | 每步一份完整快照；`invoke` 只看得到最终状态 |
| 进度标记不是结果验证 | `completed` 是 Agent 自己标的，产物要另外断言 |
